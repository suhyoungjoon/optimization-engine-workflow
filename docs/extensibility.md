# 확장 방향: 단계·agent를 끼워 넣을 수 있는 프레임워크로

M3 시점(2026-09-30)의 의견을 정리한 참고 문서다. **아직 구현하지 않은 내용**이며, 첫 번째 실제 확장(예: 레거시 데이터 로더)을 시작할 때 이 문서를 출발점으로 검토한다.

## 1. 지금 있는 것

| 구성 | 위치 | 역할 |
|---|---|---|
| 워크플로우 정의 | `workflow/pipeline.yaml`, `workflow/pipeline.py` | 단계·주체·종류(code, agent, gate)·입력·산출물·설정·코드 위치를 데이터로 선언. 스스로 맞는지 검사(`pipeline_errors`) |
| 다이어그램 | 화면 "워크플로우" 메뉴, 실행 화면의 "다이어그램" 보기 | 정의로 그린다. 단계를 추가하면 다이어그램이 따라 바뀐다 |
| 실행 순서 | `workflow/runner.py` | 단계를 **코드에서 직접** 부른다. 정의와 순서가 같은지는 `tests/test_pipeline.py`가 확인 |
| 엔진 어댑터 | `engines/` (`Engine` 프로토콜) | 엔진 교체 지점. 워크플로우는 엔진을 모른다 |

즉 "보이는 것(정의·다이어그램)"은 데이터로 분리되었고, "실행"은 아직 코드에 고정되어 있다. 확장의 다음 단계는 실행도 정의를 따르게 하는 것이다.

## 2. 확장 지점

워크플로우를 따라 끼울 수 있는 자리는 네 곳이다. 각 자리마다 입력·출력 계약을 정해 두면 agent를 바꿔 끼울 수 있다.

| 확장 지점 | 끼우는 위치 | 입력 → 출력 | 예 |
|---|---|---|---|
| 데이터 원천 | 1. 실행 앞 | 외부 데이터 → 시나리오 세트(또는 인스턴스) | 레거시 DB 로더, CSV 로더, 필드 매핑 명세 적용 |
| 분석 agent | 2. 결과분석 | 결정 레코드 → 분석 리포트(발견 목록) | 도메인 특화 분석가, 여러 분석가의 발견 병합 |
| 개선안 도출 agent | 3. 개선안 도출 | 분석 리포트 + 챔피언 params → 개선안 목록 | 파라미터 자동 탐색(plan.md M5), 규칙 기반 제안기 |
| 검증·판정 | 4. 검증 | 개선안 → 비교 결과·판정 | solver 엔진 비교(M4), 멀티에이전트 시뮬레이션 검증 |

레거시 데이터 로더는 "데이터 원천" 자리에 들어간다. 로더의 출력이 시나리오 세트 형식(`{seed, faults}` 대신 실제 데이터 식별자)을 따르면 뒤 단계는 바뀌지 않는다. 가상 데이터와 달리 **정답표가 없으므로** 정답표 채점은 쓰지 않는다(handoff 9장).

## 3. 고정 노드 (확장으로 바꿀 수 없는 것)

핵심 원칙을 지키기 위해 다음은 정의에서 빼거나 건너뛸 수 없게 한다. `pipeline_errors`가 이미 게이트 위치를 검사하고 있고, 실행을 정의 기반으로 바꿀 때 나머지도 같은 검사에 넣는다.

- **사람 승인 게이트**(`kind: gate`, 마지막 단계 하나): 자동 승인 금지(원칙 2).
- **필수조건 판정**(`pack.validate()`): 어떤 엔진·agent의 결과든 이 함수로 독립 검증(원칙 3). 검증 단계를 교체해도 위반 0건 판정은 워크플로우 코드가 한다.
- **허용 범위 검사**(`params_errors`): 개선안 도출 agent를 바꿔도 제출안은 코드가 다시 검사한다.
- **판정의 절대 기준**: 필수조건 위반 0건은 설정으로 바꿀 수 없다.

## 4. 등록 방식 제안: "화면에서 코드 업로드" 대신 "설치된 패키지를 화면에서 켜기"

화면에서 agent 코드를 올리게 하면 서버가 임의 코드를 실행하게 된다. 권장하는 방식:

1. **agent는 파이썬 패키지로 만든다.** `pyproject.toml`의 entry point로 자신을 알린다.
   ```toml
   [project.entry-points."oew.stages"]
   legacy_loader = "legacy_loader.stage:LegacyLoader"
   ```
2. **stage 계약**(구현 시 정할 초안):
   ```python
   class Stage(Protocol):
       key: str; label: str; actor: str; kind: str          # pipeline.yaml의 항목과 같은 필드
       reads: list[str]; writes: list[str]; settings: list[str]
       def run(self, ctx: StageContext) -> dict: ...        # ctx에서 reads를 꺼내 writes를 돌려준다
   ```
   `StageContext`는 실행 ID, 엔진, 챔피언 params, 앞 단계 산출물, 설정, LLM, 진행 기록(progress)을 담는다. 지금 `runner.run_workflow`가 지역 변수로 넘기는 것들이다.
3. **화면에서 하는 일**: 설치되어 발견된 stage 목록을 보여 주고, 확장 지점에 **켜기·끄기, 순서, 설정값**만 정한다. 결과는 정의 파일(`pipeline.yaml`의 사본, 또는 버전이 붙은 정의)로 저장한다.
4. **활성화 전 검사**: 계약 테스트(입력·출력 형식, 결정성 요구, 시간 예산)와 `pipeline_errors`를 통과해야 켤 수 있다. 가짜 LLM 리허설 한 바퀴를 필수로 돌린다.
5. **재현성**: 실행 기록(`run.json`)에 그 실행이 쓴 정의 버전과 각 stage 패키지의 버전을 남긴다(원칙 5).

## 5. 실행을 정의 기반으로 바꾸는 순서 (첫 확장 때)

1. `StageContext`를 만들고, 지금의 네 단계(`run_stage` 등)를 `Stage` 계약으로 감싼다. 동작은 그대로 둔다.
2. `run_workflow`를 "정의의 단계를 순서대로 `run(ctx)`"로 바꾼다. 상태 전이(`running → analyzed → ...`)는 단계별 상태 이름을 정의에 두거나, 일반화된 상태(`stage:<key>:done`)로 바꾼다. **기존 실행 기록과의 호환**을 먼저 정한다.
3. `tests/test_pipeline.py`의 순서 일치 테스트를 "정의만으로 실행된다" 테스트로 바꾼다. 기존 end-to-end 테스트가 그대로 통과해야 한다.
4. 첫 확장(레거시 로더)을 entry point로 붙이고, 데이터 원천 자리에 끼운다.
5. 화면에 "구성" 메뉴를 더해 확장 지점별로 stage를 켜고 순서를 바꾼다. 다이어그램은 이미 정의를 그리므로 추가 작업이 적다.

인터페이스를 확장 사례 없이 미리 만들지 않는 이유: 첫 실제 사례(레거시 데이터의 형식, 필드 매핑, 정답표 부재)가 계약의 모양을 정하기 때문이다. 그 전에 만든 계약은 대개 한 번 더 바뀐다.

## 6. 첫 실제 확장: M5 파라미터 탐색 (2026-10-02)

M5에서 개선안 도출과 검증 사이에 "4 파라미터 탐색" 단계를 더했다. 실행은 아직 코드에 고정되어 있어서(5장 미적용), 단계 하나를 더하는 데 다음을 손댔다. 정의 기반 실행으로 바꿀 때 줄여야 할 목록이다.

| 손댄 곳 | 정의 기반이면 |
|---|---|
| `pipeline.yaml` (단계, 산출물 `search_results`) | 그대로 (유일하게 남아야 할 곳) |
| `state.py` (상태 `searched`, 전이) | 일반화된 상태(`stage:<key>:done`)로 대체 |
| `runner.py` (호출 순서, 실패 조건, 후보 합치기) | `run(ctx)` 순서 실행 + 단계가 돌려주는 산출물 |
| `storage.py` (`3b_search.json`) | 정의의 `file`에서 읽기 |
| `stages.py` (`search_stage`) | stage 패키지 |
| 화면 (`STAGE_KEYS`, 상태 표시, 단계 패널), CLI 출력 | 단계 목록·상태는 정의에서, 단계 패널만 stage가 제공 |

배운 점:

- **산출물 하나는 한 단계만 만든다**(`pipeline_errors`)는 규칙이 설계를 정했다. 탐색 후보를 개선안 목록에 덧붙이지 않고 별도 산출물로 두고, 검증·승인이 둘을 함께 읽게 했다. 여러 agent가 같은 확장 지점에 붙는 경우(7장 열린 질문의 "경쟁")의 원형이다.
- **이전 실행과의 호환**: 탐색 이전 실행에는 `3b_search.json`이 없다. 화면은 "이 실행에는 탐색 단계가 없다"로, 승인·값 수정은 없는 파일을 빈 후보로 다룬다. 파일 이름은 기존 번호를 바꾸지 않으려고 `3b`로 했다.
- **고정 노드는 그대로였다**: 탐색 후보도 `params_errors`로 다시 검사하고, 검증 단계의 원래 판정 기준과 사람 승인을 거친다.

## 7. 열린 질문

- 한 확장 지점에 agent를 여러 개 둘 때: 순서대로(파이프), 병렬 후 병합(분석가 여러 명), 경쟁(개선안 도출기 여러 개의 안을 모두 검증) 중 무엇을 기본으로 할지.
- agent별 LLM 비용 상한: 지금은 단계별 호출 수(`settings/workflow.yaml`의 llm)만 있다. agent가 늘면 실행 단위 비용 예산이 필요하다.
- 정의 버전 관리: 정의를 바꾸면 이전 실행과 비교가 어려워진다. 정의에도 모델 레지스트리처럼 버전·이력을 둘지.
- 권한: 화면을 여럿이 쓰게 되면 구성 변경(stage 켜기)과 승인 권한을 나눌지.
- 코어와의 관계: 레거시 로더가 코어의 도메인 팩(`generate`)과 같은 자리를 차지하면, 코어 `DomainPack` 계약에 "외부 데이터로 인스턴스 만들기"가 필요할 수 있다. 이 경우 코어 레포에서 먼저 처리한다(CLAUDE.md 코어 재사용 규칙).
