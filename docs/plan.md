# optimization-engine-workflow 기획

## 1. 목적

최적화 엔진을 "모델"로 보고, 그 모델을 **실행 → 결과분석 → 개선안 도출 → 파라미터 탐색 → 검증(비교) → 개선적용**의 반복으로 계속 나아지게 하는 워크플로우 agent를 만든다.

코어 레포(`optimization-agent-harness`)는 "AI에게 맡길 수 있나"를 가리는 **비교 실험**과, 규칙 엔진 params를 개선하는 **개선 루프**를 구현했다. 이 레포는 그 개선 루프를 엔진과 무관한 **정식 워크플로우**로 만들고, 엔진을 규칙 엔진 → solver → 학습형 모델로 바꿔 끼우며 계속 업그레이드하는 자리다.

원칙은 코어 레포와 같다. AI는 제안하고, 코드는 검증하고, 사람은 결정한다.

## 2. 핵심 개념

| 개념 | 정의 |
|---|---|
| 엔진 | `DomainPack.solve` 계약을 따르는 배정 로직. 규칙 엔진(M1), solver(M4), 학습형(M5) |
| 모델 | 엔진 + params 버전. 예: `rule@v3` |
| 챔피언 | 현재 운영 기준으로 지정된 모델 버전 |
| 도전자 | 개선안을 적용한 후보 모델 |
| 시나리오 세트 | seed·결함 조합의 묶음. 학습용(개선안을 만들 때 봄)과 검증용(판정에만 씀)을 분리 |
| 모델 레지스트리 | 버전별 params 스냅샷과 모델 카드(검증 결과, 승인 정보, 부모 버전)를 보관. 챔피언 지정과 되돌리기 제공 |
| 판정 기준 | 도전자가 챔피언을 대체해도 되는지 판단하는 규칙. 필수조건 위반 0건은 절대 기준, 나머지는 설정 파일에서 사람이 정함 |

## 3. 워크플로우

```
[1 실행] → [2 결과분석] → [3 개선안 도출] → [4 파라미터 탐색] → [5 검증(비교)] → (승인 대기) → [6 개선적용]
   코드        AI+코드          AI+코드            AI+코드              코드                           사람+코드
```
(4 파라미터 탐색은 M5에서 더했다.)

| 단계 | 하는 일 | 입력 → 출력 | 코어 재사용 |
|---|---|---|---|
| 1. 실행 | 챔피언 모델을 학습용 시나리오 세트에 실행, validate·metrics | 챔피언, 시나리오 세트 → 결정 레코드, 지표 | `pack.solve`, `validate`, `metrics` |
| 2. 결과분석 | 실패 패턴과 원인 가설. 수치는 집계 도구 결과만 인용 | 결정 레코드 → 분석 리포트 | `analyze`, `Aggregator`, 근거 검사 |
| 3. 개선안 도출 | LLM이 params 변경안 제안, 코드가 허용 범위 검사 | 리포트, 챔피언 params → 개선안 목록 | `propose`, `params_errors` |
| 4. 파라미터 탐색 | AI가 바꿔 볼 파라미터와 범위를 내고, 코드가 범위 안의 조합을 학습용 세트에서 풀어 판정 규칙으로 고른다 | 리포트, 챔피언 params → 탐색 후보 | `run_tool_loop`, `params_errors`, `simulate_params` |
| 5. 검증(비교) | 개선안과 탐색 후보마다 도전자 대 챔피언을 **학습용과 검증용 세트 모두**에서 비교, 판정 기준 적용 | 개선안 → 비교표, 판정 결과 | `simulate_params`를 seed별로 반복 |
| 6. 개선적용 | 사람 승인 시 도전자를 새 버전으로 등록하고 챔피언 지정. 반려 시 기록만 | 승인 결정 → 새 모델 버전 | 레지스트리 (이 레포) |

**상태**: `running` → `analyzed` → `proposed` → `searched` → `validated` → `awaiting_approval` → `applied` / `rejected`. 중간 실패는 `failed`(사유 기록).

**상한**: 단계별 LLM 호출 수, 탐색 평가 수·시간 예산, 검증 시간 예산은 `settings/workflow.yaml`에서 읽는다.

## 4. 코어와의 관계 (handoff.md 요약)

- 코어는 고정 ref로 설치한다. 최상위 이름 `core`, `domains`, `api`, `scripts`, `configs`와 겹치는 폴더를 만들지 않는다.
- 경로 기본값이 site-packages를 가리키므로 설정·DB·캐시·params 경로는 항상 인자로 넘긴다.
- dispatch 팩의 `validate`·`metrics`는 팩 생성 시 params를 쓰므로, 후보 평가는 `pack_factory(params)`로 팩을 새로 만든다.
- 개선안 상태 전이는 코어의 API 계층에 있으므로 이 레포에서 직접 구현한다.
- 코어의 공백 중 이 레포가 채우는 것: 여러 seed·검증용 세트 비교, 판정 기준의 코드화, 되돌리기.
- LLM 경로는 코어에서도 가짜 LLM으로만 검증되었다. 이 레포도 가짜 LLM 리허설로 흐름을 먼저 고정하고, 실제 API 실험은 별도로 한다.

## 5. 엔진 로드맵

| 엔진 | 개선 대상 | 비고 |
|---|---|---|
| 규칙 엔진 (M1~) | params (가중치, 매칭 범위 등) | 코어의 dispatch 규칙 엔진을 어댑터로 감쌈. 결정적, 0.1~0.4초 |
| solver (M4) | 목적함수 가중치, 제약 완화 범위 | OR-Tools 등. 결정성(시간 제한, seed, 다중 최적해) 확보 필요. 결과는 validate로 독립 검증 |
| 학습형 (M5 이후) | 예측 + 최적화 → 배정 정책 | 실적 데이터가 쌓인 뒤 (8장). 과적합 확인을 위해 검증용 세트 필수 |

엔진을 바꿔도 워크플로우 코드는 바뀌지 않아야 한다. 이것이 이 레포가 증명할 핵심이다.

| M5 파라미터 자동 탐색 | 탐색 단계(LLM이 범위 제안, 알고리즘이 학습용 세트에서 탐색), 탐색 후보를 개선안과 같은 검증·승인으로. 학습형 엔진은 8장 순서로 미룸 | 검증용 세트 기준 개선 확인 |
| M6 레거시 데이터 로더 | 필드 매핑 명세, 레거시 내보내기(CSV) 가져오기·품질 리포트·데이터셋 스냅샷, 시나리오 세트의 과거 기간 케이스, 레거시 기준선(과거 실제 배정) 비교. 실적은 보관만 | 가상 레거시 CSV가 원래 인스턴스로 복원되고, 과거 기간 세트로 워크플로우가 돌고, 레거시 기준선 대비 비교가 나온다 |

## 7. 결정 사항

M2 전까지 열려 있던 것 (결정됨):

- 판정 기준: 목표 지표 할당성공률 평균 Δ ≥ +0.01, 부작용 한도 희망시간 일치율 하락 ≤ 0.05·이동시간 증가 ≤ 2분. 학습용·검증용 세트 모두 통과해야 통과 (`settings/workflow.yaml`, 화면 기준정보에서 수정).
- 시나리오 세트: 학습용 seed 5개 × 결함 P1~P4, 검증용 seed 10개(절반은 학습용에 없는 결함 조합).
- UI 방식: 로컬 FastAPI + 빌드 없는 단일 페이지 (M3).

M4 (2026-10-01):

- solver는 OR-Tools CP-SAT로 시작한다. 다른 solver는 비교가 필요해질 때 별도 엔진으로 추가한다.
- 3단계 매칭 범위(희망시간 ±분, 관할 밖 km)는 solver에서도 반드시 지키는 조건으로 둔다. 규칙 엔진과 같은 운영 규칙 안에서 비교하기 위해서다 (`validate()`는 매칭 범위를 검사하지 않는다).
- 목적함수: 할당 수 최대 → 희망시간 차이·이동시간 최소 → 명장 우선의 가중합. 가중치는 params에 두고 개선 루프가 조정한다.
- 시간 예산과 solver용 시나리오 세트 크기는 시제품 측정 뒤에 정한다.
- 엔진 간 비교(규칙 엔진 대 solver)는 정보로만 보여 준다. 운영 기준 엔진을 바꾸는 승인 절차는 필요가 생길 때 만든다.
- 시간 예산과 세트 (측정 후 2026-10-02): 전체 인스턴스 1회 풀이 약 15초(4스레드). solver 기본 세트는 학습용 3건·검증용 6건(`solver_train`·`solver_holdout`), 검증 예산 1200초. 시연용 세트(`demo_*`)는 케이스마다 앞 300건만 쓴다.
- solver는 결정적이라 풀이 결과를 디스크에 저장해 실행을 넘어 다시 쓴다(`runs/solver_cache/`). 같은 챔피언·세트의 풀이는 재사용되고, 새 개선안의 풀이만 새로 계산한다. `python -m workflow warm`으로 미리 채운다.
- 검증 단계의 케이스 병렬화는 하지 않는다. solver가 한 케이스 안에서 하위 문제를 병렬로 풀어 코어를 이미 다 쓴다(4코어에서 CPU 시간 ≈ 실제 시간 × 3.5, 두 케이스 동시 풀이 27.5초 대 차례로 28.8초). 코어가 많은 환경에서는 `SOLVER_THREADS`로 늘린다.
- 판정 기준은 solver에도 할당 우선(목표 지표 하나 + 부작용 한도)을 그대로 쓴다. 할당을 조금 내주고 희망시간 일치를 얻는 가중치 조정 안은 불통과가 되며, 사람이 사유를 남기고 승인(`--override-verdict`)할 수 있다. 엔진별 목표 지표(`engines.<엔진>.judgment`, 설정만으로 가능)나 여러 지표의 가중 판정은 운영 우선순위가 정해지면 다시 본다.

M5 (2026-10-02):

- 범위: 파라미터 자동 탐색만 만든다. 학습형 엔진은 실적 데이터가 없어 배울 것이 없으므로 8장 순서(레거시 로더 → 예측 + 최적화)를 따른다.
- 위치: 개선안 도출과 검증 사이의 별도 단계(4 파라미터 탐색, actor ai). 다이어그램에 보이고, 단계 확장 구조(`pipeline.yaml`)를 처음 실제로 쓴 사례다. 한 산출물은 한 단계만 만든다는 정의 규칙을 지키려고 탐색 후보는 별도 산출물(`3b_search.json`)로 두고, 검증·승인·값 수정은 개선안과 같은 번호 체계로 다룬다.
- 알고리즘: 의존성 없이 결정적인 방식. 고정 seed의 Halton 표본으로 전체 범위를 고르게 본 뒤(평가 수의 60%), 가장 좋은 점 주변을 좁혀 가며 본다. 정수 범위에서 폭이 한 칸보다 좁아지면 다시 넓힌다. Optuna 같은 베이지안 최적화는 평가가 비싸져 효율이 중요해질 때 다시 본다.
- 점수: 지금 판정 규칙(할당 우선)을 학습용 세트에 그대로 쓴다. 검증용 세트는 탐색에 쓰지 않는다.
- 부작용 한도 여유(`search.guard_margin`, 기본 0.8): 처음 구현(여유 없음)에서는 탐색이 학습용 희망시간 일치율 하락을 한도 바로 앞(−4.9%p)까지 밀어붙여, 후보 두 개가 모두 검증용에서 한도를 넘었다(−5.5%p). 탐색 중에는 한도의 80%까지만 쓰게 하자 후보가 검증용까지 통과했다. 후보끼리는 범위의 10% 이상 떨어진 점만 고른다(1위 98분, 2위 97분처럼 사실상 같은 안을 막음).
- 결과(리허설): 규칙 엔진 운영용 세트에서 탐색 1위(3단계 시간 허용 오차 89분)가 검증용 할당 +2.9%p로 판정 통과. AI가 값 하나를 정한 안(75분, +1.6%p)보다 크다. solver 시연용 세트에서도 탐색 후보 두 개가 검증용 할당 +3.0%p로 통과(AI 안 +1.7%p).
- 예산: 기본 평가 40개·300초, solver는 12개·900초(조합 하나가 학습용 3건 × 15초). solver 검증 예산은 후보가 늘어 1800초로 올렸다. 시연용 세트의 solver 리허설은 처음 약 1분 40초, 반복하면 몇 초.

M6 (2026-10-03):

- 실제 레거시 데이터가 아직 없어 개발용 가상 레거시 내보내기(`export-legacy`)로 만든다. 한글 컬럼·코드, 위경도, 날짜, 가짜 개인정보 컬럼을 쓴다. 실제 데이터가 오면 매핑 명세(`sources/legacy/mapping.yaml`)를 복사해 컬럼·코드만 고친다.
- 가상 레거시의 "실제 배정"은 규칙 엔진 v1 결과에 상황실의 수동 변경 3%(같은 지점 다른 기사, 확인 없이)를 섞었다. 레거시 기준선에서 필수조건 위반이 드러나는지(36건, 검증용 기간) 보려는 것이다.
- 코어 수정 없이 만들었다: 코어 `Instance`·`Order`·`Worker`가 일반 dataclass라 스냅샷에서 직접 만든다. 관할 경계는 코어 `load_region`을 쓴다.
- 코어 제약(다음 단계에서 코어 레포가 처리할 후보):
  1. 코드 값이 코어 `dimensions.yaml`에 고정이다 (지점 A/B/C, 매체 3종, 난이도 4종). 실제 지점·매체가 더 있으면 코어 수정.
  2. 작업자 가능시간이 하루 하나다. 날마다 다른 근무·휴무는 표현하지 못한다 (지금은 데이터셋의 작업자 행 하나).
  3. 실적(실제 소요·도착·취소)을 담을 자리가 없다. 실적으로 판정하려면 `validate()`의 작업 소요도 같은 기준이어야 한다.
- 실적은 가져와 스냅샷에 보관하고 품질 리포트에 요약만 한다. 판정·비교에는 쓰지 않는다 (예측 + 최적화 단계).
- 재현: 데이터셋 이름은 한 번 정하면 내용을 바꾸지 않는다(다른 내용이면 거부). 실행은 기간 케이스에 스냅샷 hash를 붙여 기록하고, 인스턴스를 만들 때 같은 hash인지 확인한다.
- 분할: 기간 세트는 같은 데이터셋에서 학습용이 검증용보다 앞서야 한다(겹침·역순 거부). 미래 정보가 섞이지 않게 하려는 것이다.
- 레거시 기준선은 정보용이다 (`compare-engines --baseline legacy`, 화면의 엔진 간 비교). 판정은 지금처럼 챔피언 대 도전자.
- 데이터 원천은 단계가 아니라 시나리오 세트(입력) 쪽에 붙였다. 워크플로우 단계(1~6)는 그대로다. entry point 플러그인 등록은 아직 만들지 않는다 (사례 하나).
- 개인정보: 매핑 명세에 적은 컬럼만 읽는다. `data/`는 git에서 제외한다.

### 학습형 모델링으로 가는 순서 (2026-10-01 논의)

현실의 배정은 solver의 입력 숫자(작업 소요, 이동 시간, 취소 여부 등)가 실제와 달라서 수식만으로 온전히 설명되지 않는다. 학습을 통한 모델링이 가야 할 방향이지만, 지금은 기반과 결과물이 없다.

- 가상 데이터는 생성기의 공식대로 만들어진다. 여기서 학습하면 공식을 다시 찾을 뿐이고 현실과의 간극은 배우지 못한다.
- 학습과 평가 모두 실제 실적(실제 소요 시간, 도착 시각, 취소)이 필요한데 아직 쌓이지 않았다.

그래서 다음 순서로 간다.

1. **solver 엔진 (M4)**: 엔진 교체 구조를 증명한다. 학습형도 같은 어댑터 자리에 붙는다.
2. **레거시 데이터 로더** (M6, 기반 완료): 과거 지시서·배정·실적을 가져온다. 검증용 세트를 가상 seed에서 과거 기간으로 바꾼다(백테스트). 실적으로 판정하는 것은 코어 제약 3 때문에 다음 단계와 함께 한다.
3. **예측 + 최적화**: 과거 실적으로 작업 소요·이동 시간·취소 확률을 예측하고, solver가 그 예측값으로 최적화한다. 작업 소요를 예측값으로 바꾸면 `validate()`의 작업 소요 계산도 같은 기준이어야 하므로 코어 수정이 필요할 수 있다(코어 레포에서 처리).
4. **학습형 정책 (M5 이후)**: 배정 자체를 학습한다. 범위와 검증 난이도가 가장 크다.

지금 만드는 것 중 그대로 이어지는 것: 시나리오 세트(→ 과거 기간 백테스트), 실행별 기록(→ 계획 대 실적 비교), 엔진 어댑터(→ 예측 모델을 끼울 자리).
